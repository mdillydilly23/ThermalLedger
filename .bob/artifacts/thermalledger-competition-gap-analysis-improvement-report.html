1 · Critical — Must Fix Before Submission

These items will either prevent the demo from running or will immediately undermine judge confidence in the submission's maturity.

C-1 · CORS allows only localhost — demo fails in any judge-hosted environment
backend/app/main.py hard-codes allow_origins=["http://localhost:5173"]. If a judge visits a deployment URL, every API call fails with a CORS error. The demo also exposes no way to serve the frontend over a non-localhost port without editing source code.
backend/app/main.py .env.example Effort: low
Fix
Add an ALLOWED_ORIGINS setting that defaults to ["http://localhost:5173"] and read it in the CORS middleware. Pass allow_origins=settings.allowed_origins. Add ALLOWED_ORIGINS=* (or explicit URL) to .env.example with a comment. 
# backend/app/core/config.py
allowed_origins: list[str] = ["http://localhost:5173"]

# backend/app/main.py
app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.allowed_origins,
    allow_methods=["*"],
    allow_headers=["*"],
)
C-2 · Startup crash when data/processed/ is missing
The lifespan hook raises RuntimeError if settings.data_dir does not exist. On a clean clone, data/processed/ contains committed Parquet fixtures (data/processed/evs_scores.parquet), but settings.data_dir defaults to ../data. In the Docker container, DATA_DIR=/app/data — but the Parquet files live under data/processed/ in the repo root and are bind-mounted. If someone runs the backend natively without the bind-mount the startup check passes but _load_facilities() crashes at first request with an unhandled FileNotFoundError, returning a 500 instead of a graceful 503.

C-3 · Vite dev-server Dockerfile served in production — insecure and unstable for judges
The root Dockerfile runs npm run dev -- --host 0.0.0.0. The Vite dev server is a developer tool: it includes HMR websockets, hot-module injection, and is not designed for stable public serving. Under judge load, this can fail with "Vite server exited unexpectedly" errors. It also adds ~200 MB of dev dependencies to the final image and blocks graceful shutdown.
Dockerfile Effort: low
Fix — multi-stage build + nginx
FROM node:20-slim AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html
COPY infra/nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
Also add a minimal infra/nginx.conf that proxies /api/ to the backend service. Update the docker-compose port to 80 (or keep 5173 with a note).

Every backend endpoint — including the ESG upload that writes files to disk, the verification run that spawns Celery workers and can trigger external downloads, and the report generator — requires zero authentication. This is explicitly flagged as a production gap in docs/demo-script.md, but for a public judge demo URL it is an active security risk. Any crawler hitting the submission URL can upload arbitrary files or trigger resource-intensive pipeline runs.

M-1 · No EVS score histogram / distribution chart on the Dashboard
The Dashboard shows individual facility details only when a marker is clicked. There is no aggregate view of how the full fleet of 15 facilities is distributed by EVS or flag. A judge sees isolated numbers rather than the pattern that makes the tool valuable: "3 facilities are HIGH, 6 are WATCH, 6 are CLEAR." recharts is already installed (even though it should be removed as per C-6 if unused — adding a chart makes keeping it justified).

M-2 · Coverage percentage formula has a divide-by-zero edge case
In FacilityPanel.tsx the coverage display uses: coverage_pct > 0 ? score.days_with_valid_retrievals / (score.coverage_pct / 100) : 0. When coverage_pct is very small (e.g. 0.1%), floating point produces a denominator that rounds the total-days display to an implausible value. Additionally if coverage_pct is 0 the denominator is shown as "0 days" which looks like a bug. The total days should be stored on the EVSScore model directly.
src/components/dashboard/FacilityPanel.tsx shared/evs_schema.py Effort: medium
Fix — add total_days to EVSScore and use it directly
Add total_days: int to shared/evs_schema.py. Set it in compute_evs(). Use score.total_days directly in the panel. This removes the fragile reverse-calculation and ensures the coverage fraction is always accurate.
M-3 · Prototype page "Run Verification" uses default facility selector pre-set to a specific ID
PrototypePage.tsx initialises selectedFacility to 'EPA-GHGRP-TX-001'. If this facility is not in the loaded facilities list (e.g. a custom dataset), the selector shows a blank selected option. More importantly, judges may not notice this is a hardcoded default and miss the "All facilities" option. A default of 'all' is safer and more impressive to open with.
src/pages/PrototypePage.tsx Effort: low

4 · Low Priority — Optional Refinements

L-1 · Frontend has no error boundary — a render crash shows a blank white page
There is no React ErrorBoundary wrapping the application. If any component throws during render (e.g. malformed API response, unexpected null), the entire app goes blank with no user-visible message.
src/main.tsxEffort: low✓ Resolved
Fix — implemented in src/main.tsx
An ErrorBoundary class component was added directly in src/main.tsx and wraps the full provider tree. On any unhandled render error it displays a centred "Something went wrong" message with a Reload button that calls window.location.reload(). 
class ErrorBoundary extends React.Component<React.PropsWithChildren, {hasError:boolean}> {
  static getDerivedStateFromError() { return { hasError: true } }
  render() {
    if (this.state.hasError) return (
      <div style={{padding:'48px 24px',textAlign:'center'}}>
        <h2>Something went wrong</h2>
        <button onClick={()=>window.location.reload()}>Reload</button>
      </div>
    )
    return this.props.children
  }
}

// In render:
<ErrorBoundary>
  <QueryClientProvider client={queryClient}><App /></QueryClientProvider>
</ErrorBoundary>
L-2 · Task polling does not use exponential backoff after repeated errors
useTask.ts retried after POLL_INTERVAL_MS * 2 (3 s) on any error, indefinitely. If the backend is down, this floods the server with requests. Exponential backoff with a cap (e.g. max 30 s) is more polished.
src/hooks/useTask.tsEffort: low✓ Resolved
Fix — implemented in src/hooks/useTask.ts
An errorCount counter is tracked inside the effect. On each consecutive failure the backoff doubles: POLL_INTERVAL_MS × 2^errorCount, capped at MAX_BACKOFF_MS = 30 000 ms. The counter resets to 0 on a successful poll. 
const MAX_BACKOFF_MS = 30_000
let errorCount = 0

// on success:
errorCount = 0

// on catch:
errorCount++
const backoff = Math.min(POLL_INTERVAL_MS * 2 ** errorCount, MAX_BACKOFF_MS)
setTimeout(poll, backoff)

5 · Competitive Edge — Innovative Differentiators

These additions are not currently in the codebase but would make ThermalLedger stand out in the AI Builders Challenge judging. Each targets a specific scoring dimension: IBM technology depth, real-world impact, or demo memorability.

E-1 · Add a "Explain this EVS score" Granite chat widget to the facility panel
Currently, Granite is only used for ESG document parsing and report generation. Adding a conversational Q&A widget in the FacilityPanel — "Why is this facility flagged HIGH?", "What does the uncertainty interval mean for this claim?" — would demonstrate sophisticated, contextual AI use rather than one-shot extraction. This directly showcases IBM Granite's instruction-following capability in an interactive way that most competitors will not have. The backend can pass the EVS score JSON as context and use the existing GraniteClient live path.
Effort: highIBM Granite integration depth
Implementation approach
Add POST /facilities/{id}/explain to the backend (calls ML service /granite/explain). In the ML service, build a prompt that includes the EVS JSON and the user's question. Stream the response using SSE or poll a short Celery task. Render in the panel as a simple chat UI. Keep a fixed context window (just the EVS data, no conversation history needed).
E-2 · Add an EVS trend chart — show score history across multiple observation windows
The EVS score is shown as a single point-in-time number. The Parquet store already supports multiple records per facility (the upsert replaces rather than appends, but this could be changed to keep history). A sparkline or bar chart showing EVS over time — even with 2–3 synthetic historical points from the fixture — would convey the platform's ongoing monitoring value proposition. This is the difference between a one-time audit tool and a continuous compliance platform.
Effort: mediumImpact storytelling
Implementation approach
Add a history array to the fixture Parquet (3 rows per facility at different dates). Add GET /facilities/{id}/history endpoint. Render a small inline bar chart in FacilityPanel using recharts (already installed) showing EVS at each observation date.
E-3 · Integrate IBM EIS (Environmental Intelligence Suite) satellite imagery API
The config.py already has eis_api_key and eis_base_url as settings placeholders. IBM EIS provides actual satellite-based environmental data APIs. Using EIS as an additional data source — even for a single demo facility — would make the IBM technology story much stronger and demonstrate real API integration beyond Granite. The eis_base_url defaults to https://api.ibm.com/geospatial/run/na/core/v3.
Effort: highIBM EIS integration
Implementation approach
Add an EIS client service in backend/app/services/eis_client.py. Use it as a third data source in backend/app/core/data_source.py alongside the existing local/remote toggle. Show an "EIS live" badge in the Prototype readiness panel when EIS_API_KEY is configured.
E-4 · Add watsonx.data (Presto) federated query path for facility registry
The config has watsonxdata_host, watsonxdata_port, and watsonxdata_access_token as placeholders. The facility registry is currently a flat CSV. Connecting the registry query to IBM watsonx.data — even if the underlying data is the same — would demonstrate the watsonx platform breadth that the IBM challenge scoring criteria explicitly value. Judges looking for "IBM technology integration" beyond Granite will reward this.
Effort: highIBM watsonx.data
E-5 · Add a one-page "Architecture & IBM Technology" section to the README
The README is technically accurate but reads as developer setup documentation rather than a competition submission. Judges need to quickly understand: what problem is being solved, how IBM technology is central to the solution (not just an add-on), and what the demo proves. A dedicated "How IBM Technology Powers ThermalLedger" section — covering Granite (ESG extraction + report generation), watsonx.ai (scoring), the local audit fallback as proxy for OpenPages + Hyperledger Fabric, and the data pipeline — would significantly improve first impressions from non-technical judges.
